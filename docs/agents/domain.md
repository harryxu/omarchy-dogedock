# Domain docs

DogeDock uses a single-context layout. Keep the glossary at the repository root in `GLOSSARY.md` and architecture decision records (ADRs) in `docs/adr/`.

Before exploring the code, read the glossary and the ADRs relevant to the work if they exist. Continue with the task when either is absent. Use the domain-modeling skill to add a glossary or ADR when the team settles its first term or records its first decision.

Use glossary terms in issue titles, proposals, hypotheses, and test names. When a term is missing, check the project's existing vocabulary and bring genuine gaps to domain modeling.

If a proposal conflicts with an ADR, name the ADR and explain why the decision should be revisited.
